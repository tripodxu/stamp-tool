# 轻量公章盖章工具 — 设计文档

> 版本 v0.1 · 状态：待实现
> 范围：v1 仅支持 **PDF → PDF**。图片输入、Word 输入列为后续项（见 §8）。

---

## 1. 目标与非目标

### 目标
用户上传一份 PDF 和一枚背景透明的公章图片，在浏览器中自由调整公章的位置、大小、旋转与不透明度，导出为带章 PDF。

### 非目标（v1 明确不做）
- OCR / 文本识别 / 语义理解
- 自动识别落款位置
- Word（.docx）、Excel、网页等非 PDF 输入
- 多章批量盖、多文件队列、账号体系、服务端存储
- 骑缝章、跨页章、PDF/A 归档、加密输出
- 对已数字签名的 PDF 做合法签名

## 2. 第一性原理

### 2.1 问题归约

盖章操作的本质是一个函数：

```
输出 = stamp(文档, 印章, 仿射变换)
```

即：**把一个带 alpha 通道的图，经平移/缩放/旋转后，合成到文档页面的某个物理位置。**

这个函数**不需要理解文档内容** —— 盖章不改变文字、不改变排版、不需要知道段落含义。因此：

- OCR、版面分析、语义定位等能力全部不需要；
- "自动放到落款处"在本质上是做不到的伪需求，只能人工拖拽解决；
- 多页、撤销、批量等需求都是同一原语的周边工程，不是核心难点。

### 2.2 文档空间的两种形态

| 形态 | 输入 | 编辑表示 | 导出路径 |
|---|---|---|---|
| 固定光栅 | jpg / png / 扫描件 | 单个像素画布 | Canvas 合成 → toBlob |
| 矢量分页 | **PDF** | 页面空间（pt） | 往原内容流追加 XObject 绘制 |

其他格式最终都落到这两种之一。v1 只做第二种。

## 3. 由第一性原理推出的四条架构决策

### 决策 1：编辑期不修改文档像素 → 预览层与导出层彻底解耦

这是最核心的架构结论。

因为盖章**不改变**原文档的任何像素：

- **预览**：pdf.js 把当前页渲染成 canvas；印章是一个**绝对定位的 `<img>`**，用 CSS `transform: translate() rotate()` 定位。
  - 拖拽 = 改两个 CSS 变量。
  - **不需要 Konva / Fabric / 任何画布编辑器库。**
- **导出**：pdf-lib 打开原始 PDF，在页面上 `drawImage(嵌入的原始 PNG)`。
  - **完全不重新渲染文档。** 文字仍是文字、字体仍是原字体、矢量零损失。

代价与收益：预览里印章是被 CSS 缩放的位图，导出嵌入的是原图 —— **导出质量恒 ≥ 预览质量**。

> 推论：这也是本项目**不做 PDF 内实时像素合成预览**的原因 —— 那需要每次拖拽重渲染整页，性能与实现复杂度都暴涨，而用户看不出差别。

### 决策 2：白纸底 ⇒ alpha 混合 ≡ 正片叠底 ⇒ 无需注入 ExtGState

物理上印油是减色材料，正确混合模式是 `multiply`。但 PDF 使用 `multiply` 需向内容流注入 `/BM /Multiply` 的 ExtGState，pdf-lib 不直接支持，是显著工程成本。

数学上推一下就不需要了：

```
alpha 合成:  C_out = α·S + (1−α)·B
正片叠底:    C_out = α·S + (1−α)·B·D/255,  D = 底图
当 D = 白色(255):  两式完全等价
```

**结论：底图为白纸时，普通 alpha 与 multiply 在数学上等价，直接用 alpha 即可，不碰 ExtGState。**

> 例外（已知限制）：印章盖在照片 / 深色底图上时存在物理失真。v1 对图片类输入不做此项；若未来支持，需引入 `darken` 或放弃图片输入。

### 决策 3：印章有法定物理尺寸 → 坐标系必须是物理单位

公章直径法定（常见 40mm / 42mm）。若按屏幕像素存位置，换缩放比例或导出尺寸时印章会变形。

PDF 用户空间本身即 **1 pt = 1/72 inch = 0.35278 mm**，A4 = 595.28 × 841.89 pt。**换算是精确常数，无需经验系数。**

约定：

- **存储**：一律用 **PDF point**，原点为页面**左上角**，y 轴向下（与屏幕一致，减少一次翻转的心智负担）
- **显示**：UI 上以 **mm** 呈现
- **导出**：直接就是 PDF 原生坐标，零转换误差

配套的**分辨率体检**（用户感知价值高）：

```
所需像素宽 = mm × DPI / 25.4
40mm @300dpi = 472px      ← 合格下限
40mm @600dpi = 945px
低于 300dpi 上限 → 提示"印出来会糊"
```

### 决策 4：编辑期不改文档 ⇒ 撤销是免费的

文档不可变，可变的只有印章数组。因此：

```
state  = Stamp[]              // 唯一可变状态
undo   = state 的快照栈        // 深度 20，数十行代码
```

无需任何 diff / patch 算法。

## 4. 技术选型

| 层 | 选择 | 理由 |
|---|---|---|
| 构建 | Vite + React + TypeScript | 工具栏、表单、撤销状态的收益明显 |
| 文档渲染 | `pdfjs-dist` | **仅用于显示**，不参与输出 |
| 文档写入 | `pdf-lib` | 纯 JS，浏览器内可直接操作 PDF |
| 印章交互 | **原生 CSS transform** | 见决策 1，不引入画布库 |
| 部署 | 纯静态（GitHub Pages / Vercel / 本地 `dist`） | 无后端 ⇒ 无存储、无合规成本 |

### 已知实现风险

1. **pdf.js worker 打包**：Vite 下最常见报错点。需将 `pdf.worker.mjs` 作为静态资源引入并设置 `GlobalWorkerOptions.workerSrc`。
2. **pdf-lib 维护节奏**：近年以修 bug 为主，但 API 稳定、能力足够。若需更新能力，社区有保持 API 兼容的 fork 可替换。
3. **替换 pdf.js 为其他渲染库不可行**：决策 1 的解耦依赖于"渲染器只负责看"，任何"所见即所得即导出"的方案都会推翻架构。

## 5. 数据模型

```ts
type Stamp = {
  pageIndex: number
  pngBytes:  Uint8Array   // 原始 PNG 字节，导出时无损嵌入
  xPt: number
  yPt: number             // 相对页面左上角，单位 pt
  widthPt: number         // 默认 40mm = 113.386 pt
  rotationDeg: number     // 实际盖章常有轻微倾斜
  opacity: number         // 0..1
}

type PageInfo = { wPt: number; hPt: number }

type AppState = {
  doc: { pages: PageInfo[] }
  stamps: Stamp[]
  currentPage: number
  zoom: number
  selectedId: string | null
  history: Stamp[][]     // 快照栈，深度 20
}
```

### 单位与坐标换算（唯一真源，写死为常量）

```
mm  → pt :  pt = mm * 72 / 25.4
pt  → mm :  mm = pt * 25.4 / 72
y 轴翻转:  pdfY = pageHeightPt - (yTopDown + heightPt)
屏幕缩放:  screen = pt * zoom * (devicePixelRatio 仅用于 canvas 像素密度，不影响逻辑坐标)
```

## 6. 已知风险与对策

按遇到概率排序。

| # | 问题 | 现象 | 对策 |
|---|---|---|---|
| 1 | **印章 PNG 白边** | Photoshop 导出的"透明 PNG"实为「未预乘 alpha + 白底」，盖在有色内容上出现白色毛边 | 检测「alpha > 0 但 RGB ≈ 255」的像素占比；提供**一键去白边 + 裁剪到墨迹实际边界**。此功能直接决定成品观感，优先级等同核心功能 |
| 2 | **PDF 加密** | 有所有者密码保护的 PDF 无法追加内容 | 捕获 `PasswordException`，明确提示"该 PDF 受保护，无法盖章" |
| 3 | **已数字签名的 PDF** | 追加内容导致签名失效，Adobe 打开提示"文档已被修改" | 事前检测签名域，事前警告 |
| 4 | **超大 PDF** | 100MB 文件内存溢出 | 按需渲染**当前页**（架构 1 天然支持，无需全量位图） |
| 5 | **印章图像质量不足** | 导出后打印模糊 | 决策 3 的分辨率体检，上传时即提示 |
| 6 | **浏览器差异** | Safari 对大 canvas / WebAssembly 内存限制更严 | 目标浏览器定为 Chrome / Edge 最新两个大版本 |

## 7. 实现顺序

每步独立可验收。

| 步 | 内容 | 验收标准 |
|---|---|---|
| 1 | 打通管道 | 载入 PDF → 渲染首页 → 导出无章 PDF，pdf.js 与 pdf-lib 在构建环境均正常 |
| 2 | **核心闭环** | 上传印章 → 拖拽 → 缩放 → 导出带章 PDF。**此步完成产品已可用** |
| 3 | 多页 | 翻页导航、每页独立印章、导出全部页 |
| 4 | 精确控制 | mm 尺寸输入（默认 40mm）、旋转、不透明度、方向键 1mm 微调（Shift 为 10 倍） |
| 5 | 可用性 | 撤销/重做、多章共存、删除、分辨率体检 |
| 6 | 打磨 | 缩放适配、落款位预设、去白边、导出 PNG/JPEG 选项 |
| 7 | 打包 | 静态构建、本地双击可用或托管 |

## 8. 后续项（明确不在 v1）

| 项 | 难度 | 说明 |
|---|---|---|
| 图片输入（jpg/png/扫描件） | 低（≈30 行） | Canvas 路线：`drawImage` + `toBlob`。注意 JPEG 重编码有损，需提示 |
| 盖章日期文字 | 中 | **绕开中文字体坑**：导出时用 canvas 将印章 + 日期合成成一张 PNG 再嵌入。牺牲文字矢量性，换零字体负担 |
| Word 输入 | **高，不建议** | Word 存在内联/浮动两套锚点 + DrawingML + 排版重排。推荐路径：Word → 打印为 PDF → 本工具 |
| 骑缝章 / 跨页章 | 中 | 需按页宽切分印章图像 |
| 批量盖章 | 中 | 需引入文件队列与模板复用 |

## 9. 非技术说明

印章图片应来自使用者**有权使用的**合法印章。工具本身仅做图像合成，不产生任何具有法律效力的电子签章；输出文件不等同于《电子签名法》意义上的可靠电子签名，其法律效力取决于接收方是否采信。
